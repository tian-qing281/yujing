## A. 立项与定位（5）

**A1. 一句话介绍项目？**
舆镜（YuJing）是一个 8 平台热搜聚合 + 多维 AI 分析（聚类 / 情感 / ABSA / Agent 对话 / 个性化推荐）的一站式中文舆情监控系统，让用户用一个 Web 界面追完所有平台热点，并能用自然语言追问深度问题。

**A2. 跟「今日热榜」「鱼皮热点监控」有什么区别？**
他们是「**热搜聚合器**」——把各平台 TopN 列出来；我们在这之上加了三层：（1）跨平台事件聚类把同一事件合并；（2）8 分类细粒度情感 + 方面级分析；（3）Agent 自然语言问答。

**A3. 为什么不直接调用现成的 LLM 让它去爬？**
LLM 没有结构化数据底座，每次问都要重新检索 + 推理，慢且不可控。我们的设计是「**数据库做主，LLM 做表达**」——所有事实由工具返回，LLM 只负责组织语言。

**A4. 目标用户是谁？**
PR / 公关团队、政务舆情员、新闻从业者、做行业研究的学生。不是 C 端 toC 信息流。

**A5. 商业化方向？**
（1）订阅制 SaaS（按数据源 / 用户量收费）；（2）私有化部署给政府 / 大企业；（3）数据 API 出售。

## B. 技术选型（10）

**B1. 为什么用 FastAPI 不是 Django？**
异步 IO 原生支持（爬虫并发 + LLM 流式 + SSE 一锅出），依赖注入轻量，OpenAPI 自动生成。Django ORM 强但同步阻塞场景不适合 LLM 流式。

**B2. 为什么 SQLite 不是 PostgreSQL？**
单机部署 + 零运维 + 文件级备份。读写量 < 100 QPS，SQLite WAL 模式完全够。生产规模到达后切 PG，ORM 抽象层 SQLAlchemy 无缝。

**B3. 为什么 BGE-small-zh-v1.5 不是 BGE-base 或 m3？**
small 512 维：（1）CPU 推理 16 篇 / 秒，base 只 5 篇；（2）C-MTEB 中文 STS 上 small 0.65 vs base 0.69，差距小；（3）显存友好。多语场景计划升 m3。

**B4. 为什么用 MeiliSearch 不是 Elasticsearch？**
Meili 单二进制 50MB，零配置启动；ES 要 JVM + 配置 + 调优。功能上 typo-tolerant、中文分词够用，QPS 在我们场景没瓶颈。

**B5. 为什么用 FAISS 不是 Milvus / Qdrant？**
我们的索引就在 FastAPI 进程内，FAISS in-process 零网络开销；Milvus 适合多服务共享向量库。规模上去后会迁。

**B6. 为什么用 DeepSeek 不是 GPT-4？**
中文场景 deepseek-chat 质量已接近 GPT-3.5；价格 0.001 元 / 千 token，是 GPT-4 的 1/100；国内不需要代理。提供 OpenAI 一键切换。

**B7. 为什么用 Vue 不是 React？**
Vue 3 + Composition API + Vite 启动 < 1s 开发体验好；项目体量中等不需要 React 的复杂生态。

**B8. 为什么用 APScheduler 不是 Celery？**
APScheduler 进程内调度，零额外组件（不要 Redis / RabbitMQ）；任务量小（每 5 min / 30 min / 2h 各一个），Celery 杀鸡用牛刀。

**B9. 为什么聚类用 Union-Find + 阈值不是 HDBSCAN？**
（1）支持增量；（2）已有 Event 持久化实体，HDBSCAN 重跑会乱簇 id；（3）阈值可解释、可调。

**B10. 为什么 11 个 Agent 工具不合并？**
单一职责原则。每个工具一个文件 200 行内，参数 schema 清晰，LLM 也更容易选对。合并会导致参数膨胀，LLM 容易传错参。

## C. 算法细节（15）

**C1. 聚类阈值 0.62 / 0.69 怎么定的？**
线下 200 对人工标注，P-R 曲线最佳点。详见 [算法/聚类算法.md](算法/聚类算法.md) Q1。

**C2. 增量聚类阈值为什么比全量高？**
不可逆决策，宁可多建簇也不要污染老簇；下次全量 rebuild 会合并。

**C3. 复合相似度公式各权重怎么定？**
经验值 + 小样本调优：cos 主导（0.60），time 辅助消歧（0.25），platform 微调（0.15）。time 项半衰期 12h 来自「新闻热度典型生命周期 ≈ 1 天」观察。

**C4. Centroid 漂移怎么解决？**
每 2h `_run_centroid_calibrate_job` 重算所有近 7 天事件的 centroid（平均所有文章向量），消除增量顺序偏差。

**C5. 情感为什么 8 类不是 3 类？**
3 类太粗，无法支撑「按 concern 排序」「按 anger 推荐」业务。8 类对齐 Ekman 6 + 中性 + concern（中文特有担忧）。

**C6. BERT 模型选 Johnson8187 的理由？**
HuggingFace 公开模型，中文情感 macro F1 ≈ 0.72；不需要自训。

**C7. BERT 失败怎么办？**
即时降级到关键词规则（[sentiment_rules.py](../app/services/sentiment_rules.py)），8 类各 30-80 个种子词。F1 降到 0.42 但保证主流程不挂。

**C8. ABSA 为什么用 LLM 不用监督模型？**
新闻方面是开放集（车型 / 价格 / 智驾 vs 财报 / 股价 / 管理层），监督模型方面词表覆盖不了。LLM 抽取 F1 ≈ 0.68 且可解释。

**C9. ABSA 怎么防 LLM 幻觉？**
（1）prompt 强制只能从原文抽取；（2）方面 ≤ 6 字、reason ≤ 30 字限制；（3）输出非 JSON 直接 fallback 空数组。

**C10. 推荐排序怎么算？**
融合分 = `keyword_match * 5 + source_weight * 3 + profile_source * 3 + profile_tag * 3 + semantic_sim * 4`。其中 semantic_sim 是订阅向量与事件 centroid 的余弦相似度。

**C11. 用户画像怎么推断？**
取最近 50 条浏览 → 提取 jieba TextRank 关键词 → 在事件库 KNN 召回 80 个相似事件 → 用户没看过且 cos ≥ 0.55 → 聚合关键词加权 → 写 `UserProfile.inferred_tags`。30 min TTL。

**C12. Agent 怎么防止编造事件？**
（1）System Prompt 强约束：仅基于工具返回；（2）工具返回带 event_id，回答必须引用；（3）线下抽样校验 hallucination rate。

**C13. Agent MAX_STEPS=8 怎么定？**
生产 P99 = 7 步，留 1 步缓冲。再高 LLM 容易陷入「反思 → 重调同工具」死循环。

**C14. Centroid 用算术平均 vs 加权？**
当前是算术平均（每文章等权）。考虑过按 heat_score 加权，但热度本身波动大会引入更多噪声，且校准频率高（2h）足以纠偏。

**C15. 怎么处理跨语言文章？**
当前 BGE 是中文模型，英文 fallback 到 jieba TextRank（效果一般）。规划升级 bge-m3 多语模型。

## D. 工程难点（10）

**D1. 8 个爬虫并发怎么调度？**
每源独立 interval（120s / 600s），APScheduler 错峰；HTTP 请求用 ThreadPoolExecutor max=10。失败不阻塞主流程，单源挂了其他源继续。

**D2. Cookie 失效怎么处理？**
（1）`POST /api/cookies/save` 用户手动更新；（2）`GET /api/cookies/check/{source}` 校验有效性；（3）失效后该源降级返回空数组，前端 UI 提示「Cookie 已失效」。

**D3. LLM 限流怎么办？**
（1）`asyncio.Semaphore(3)` 全局并发上限；（2）重试 2 次指数退避；（3）30s 超时；（4）失败返回模板答案不阻塞用户。

**D4. SQLite 写竞争？**
WAL 模式 + SQLAlchemy 单 engine 单 connection pool；爬虫批量写包 transaction；读写比 ≈ 10:1 没观察到锁竞争。

**D5. 早报怎么不每次都重算？**
每天 08:00 调度一次写文件缓存 `runtime/cache/morning_brief/{date}.md`；用户请求走 `GET /api/ai/morning_brief/cached` 直返。

**D6. 向量索引重建会卡用户请求吗？**
后台 task 跑，写入新索引完成后原子替换全局变量；读取无锁。

**D7. FAISS 索引怎么持久化？**
启动时从 `ArticleEmbedding` 表（512-d BLOB）重建；不写 .index 文件避免一致性问题。重建耗时 ≈ 1s / 万条。

**D8. 前端 SSE 断线重连？**
EventSource 原生重连；前端记录最后 event_id，后端按 event_id 续传（目前未实现，未来）。

**D9. 怎么测试 Agent 工具？**
每个 tool 单独 unit test（pytest），mock LLM 只测工具逻辑；端到端测试通过对话脚本，断言 final answer 包含特定关键词。

**D10. 部署怎么单机一台？**
FastAPI + uvicorn + SQLite + MeiliSearch（单二进制）+ FAISS（in-process）全在一台机器，资源 4C8G 起。详见 [部署文档.md](部署文档.md)。

## E. 评测与指标（5）

**E1. 聚类质量怎么评？**
200 对人工标注，计算 Precision / Recall。当前 P=0.91 R=0.82 F1=0.86。详见 [评测指标文档.md](评测指标文档.md)。

**E2. 情感准确率？**
BERT 路径线下 300 样本 macro F1=0.71；规则降级 F1=0.42。

**E3. 推荐效果？**
线下重放 + 离线指标 NDCG@10 / Hit@10。无在线 A/B（用户少），离线 NDCG@10 ≈ 0.63。

**E4. Agent 成功率？**
100 轮人工评估，「答非所问」率 < 8%，「幻觉事件」率 < 3%。

**E5. 系统性能瓶颈？**
BGE 向量化首次（CPU 6s/100 篇），缓存命中后基本无瓶颈。LLM 调用是单次最长延迟（1-2s）。

## F. 设计权衡（5）

**F1. 为什么不做用户登录系统？**
比赛 demo 定位，单用户模式简化部署。`UserProfile` 表预留 `user_id` 字段，未来扩展容易。

**F2. 为什么没用消息队列？**
单机量级用不到。APScheduler 进程内调度 + asyncio.Queue 替代了简单的任务排队。

**F3. 为什么没缓存层（Redis）？**
SQLite 本身 + 进程内字典已够。规模上去后会上 Redis 缓存 SWR / 早报 / 画像。

**F4. 为什么聚类不实时？**
新闻事件不需要秒级感知，30min 增量已经足够；实时聚类会导致簇频繁抖动，前端 UX 反而差。

**F5. 为什么不用 GraphQL？**
端点少（< 50），REST 清晰；GraphQL 会增加学习成本和测试难度。

## G. 创新点速答（5）

**G1. 项目最大创新点？**
（1）跨平台事件聚类（业界少有把 8 平台事件粒度合并的）；（2）8 分类细粒度情感 + 方面级 LLM 抽取联用；（3）数据库驱动的 Agent（保证答案不幻觉）。

**G2. 相比现有产品最强差异？**
对比鱼皮 / 今日热榜（聚合器），我们多了「**事件维度的深度分析**」，让用户能问「为什么这个事件 negative」「跟昨天的事件相比怎么样」。

**G3. 用了哪些前沿技术？**
BGE 向量化、FAISS ANN、LLM tool_call 协议、SSE 流式、APScheduler、SQLAlchemy 异步。

**G4. 数据规模？**
连续运行一周 ≈ 5 万文章 / 6000 事件 / 1500 主题，单机 SQLite < 500MB。

**G5. 还能怎么扩展？**
（1）接入更多源（小红书、抖音）；（2）BGE 升级 m3 支持多语；（3）做用户登录 + 多租户；（4）Agent 加更多业务工具（如导出周报）。
