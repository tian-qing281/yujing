## 1. 🟢 文章热度评分 (Article Scoring)

算法位置：`app/services/events.py` → `_score_article()`

评分函数量化单篇情报的"研判价值"，用于事件级 heat_score 计算。

### 1.1 公式

```text
Score = max(0, 120 - rank) + min(hot_value / 10000, 160) + source_bonus
```

| 分项 | 公式 | 含义 |
|:---|:---|:---|
| 位次激励 | `max(0, 120 - rank)` | 直接采信平台编辑排名意图 |
| 热度倍率（带上限） | `min(hot_value / 10000, 160)` | 160 分安全阀，防止爆款淹没敏感信号 |
| 基座源奖励 | 微博/知乎 → +20 分 | 高权重核心信源加分 |

### 1.2 演算案例

| 场景 | 排名 | 热度 | 得分 |
|:---|:---|:---|:---|
| 微博顶流热搜 | #1 | 5,000,000 | `119 + 160 + 20 = 299`（理论峰值） |
| 二线平台中型热点 | #30 | 50,000 | `90 + 5 + 0 = 95` |
| 小众敏感信号 | #99 | 1,000 | `21 + 0.1 + 0 ≈ 21` |

## 2. 🟢 事件影响指数 (heat_score)

算法位置：`app/services/events.py` → `_build_cluster_payload()`

### 2.1 公式

```text
heat_score = avg(top3_article_scores) + min((platform_count - 1) × 30, 150) + log₂(article_count) × 15
```

| 分项 | 取值范围 | 含义 |
|:---|:---|:---|
| Top-3 文章热度均值 | 0 ~ 299 | 事件内最强信号强度 |
| 跨平台奖励 | 0 ~ 150 | 多域覆盖传播力 |
| 数量对数奖励 | 0 ~ ~100 | 信息量边际递减增益 |

### 2.2 演算案例

| 事件 | Top-3 均分 | 平台数 | 文章数 | heat_score |
|:---|:---:|:---:|:---:|:---:|
| 顶级跨域 | 280 | 6 | 32 | `280 + 150 + 75 = 505` |
| 单平台热点 | 200 | 1 | 8 | `200 + 0 + 45 = 245` |
| 低强度信号 | 50 | 1 | 2 | `50 + 0 + 15 = 65` |

## 4. 🟢 事件排序策略

算法位置：`app/api/routes.py` + 前端 `yujing-ui/src/App.vue::compareEvents`

### 4.1 默认排序（后端）

事件列表（`/api/events`）默认按 **`heat_score DESC, latest_article_time DESC, id DESC`** 排序。

### 4.2 时间窗口自适应

统一搜索 `/api/search/unified` 中：
- **长时间窗口（>24h）**: `article_count DESC, latest_article_time DESC, id DESC` → 热度优先
- **短时间窗口（≤24h）**: `latest_article_time DESC, article_count DESC, id DESC` → 时效优先

### 4.3 稳定化 tiebreaker

**Bug 观察**：初版排序仅以 `heat_score / article_count / latest_article_time` 为键，同值行在 SQLite 中返回顺序不确定；叠加 `limit(9)` 后每次刷新取到的 Top 9 集合都可能在同分事件间漂移，前端表现为"闪一下换卡片"。

**修法**：所有排序子句尾部统一加 `Event.id.desc()` 作稳定 tiebreaker，影响：

| 端点 | Before | After |
|:---|:---|:---|
| `/api/events` | `heat_score DESC, latest_article_time DESC` | + `id DESC` |
| `/api/search/unified` (high_heat) | `article_count DESC, latest_article_time DESC` | + `id DESC` |
| `/api/search/unified` (短窗口) | `latest_article_time DESC, article_count DESC` | + `id DESC` |
| `search_events` (服务层) | `latest_article_time DESC, article_count DESC` | + `id DESC` |

### 4.4 前端 `compareEvents` 分级整数比较

为什么前端不用加权浮点公式：

```js
// 失败方案（已废弃）：
// heat_score 是后端 rebuild 时写入的浮点，两次 Ctrl+F5 之间若 scheduler 触发过 rebuild
// 分数会微变 → sort 结果随之漂移；加权公式的浮点减法本身也可能引入 ±ε 的不稳定比较。
// score = article_count * 4 + platform_count * 6 + heat_score

// 最终方案（生产）：分级整数比较，同一批数据顺序绝对稳定
const compareEvents = (a, b) => {
  if (a.article_count !== b.article_count) return b.article_count - a.article_count;
  if (a.platform_count !== b.platform_count) return b.platform_count - a.platform_count;
  return b.id - a.id;
};
```

### 4.5 双 fetch 并发双写修复

前端有两处会写 `events.value`：
- `watch(activePlatform, immediate: true)` → `scheduleEventHubHydration` → 旧 `fetchEvents` (`/api/events`)
- `onMounted` → `fetchUnifiedSearch` (`/api/search/unified`)

两个接口 ORDER BY 不同 + 各自 `limit(9)`，并发返回的两批事件集合**不完全相同**（一批热度优先、一批时间优先）→ 前后两次渲染换卡片。修法：`scheduleEventHubHydration` 不再调 `fetchEvents`，统一走 `fetchUnifiedSearch`，单一写入通道 + `requestId` + `AbortController` 并发保护。

## 5. 🟢 前端 `impactScore`（0-100 归一化影响指数）

算法位置：`yujing-ui/src/utils/dataAdapter.js::calculateImpactScore`

前端在组件层对热搜条目做的归一化影响力分数，与后端 `heat_score`（事件级）**相互独立**：后端 `heat_score` 度量事件级影响力（可达 500+），前端 `impactScore` 度量单条热搜的相对影响力（0-100）。

### 5.1 公式

```text
baseScore = max(40, 100 - rank * 1.5)
bonus = 平台加成（最多 +10）
impactScore = round(baseScore + bonus)   # 截断到 [0, 100]
```

| 条件 | 得分 |
|:---|:---|
| 热搜第 1 名 (rank=1) | baseScore = 98.5 |
| 第 10 名 (rank=10) | baseScore = 85 |
| 第 40 名 (rank=40) | baseScore = 40（触底） |
| 微博平台加成 | `min(10, hot_score / 200000)` |
| 知乎平台加成 | `min(10, hot_score / 100)` |
| B 站平台加成 | `min(10, view / 500000)` |
| 其他平台 | 0 |

### 5.2 演算案例

| 场景 | rank | hot_value | impactScore |
|:---|:---:|:---:|:---:|
| 微博顶流热搜 | #1 | 5,000,000 | `98.5 + 10 ≈ 99` |
| 知乎中型热点 | #8 | 3,000 | `88 + 10 = 98` |
| B 站尾部视频 | #45 | 100,000 | `40 + 0.2 ≈ 40` |

### 5.3 与 `heat_score` 的关系

| 概念 | 位置 | 度量 | 范围 |
|:---|:---|:---|:---|
| `impactScore` | 前端 | **单条热搜条目相对影响力**（rank+平台热度） | 0-100 |
| `heat_score` | 后端 | **事件级综合影响力**（Top3 文章得分+跨平台+数量） | 0-500+ |

前端卡片显示的"99 影响指数"来自 `impactScore`，描述该条热搜在当前平台的相对热度；事件列表排序按 `heat_score`（和前者无直接关系）。
