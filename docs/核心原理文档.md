## 1. 🟢 文章热度评分 (Article Scoring)

算法位置：`app/services/events.py` → `_score_article()`

评分函数量化单篇情报的"研判价值"，用于事件级 heat_score 计算。

### 1.1 公式

```text
Score = max(0, 120 - rank) + min(hot_value / 10000, 160) + source_bonus
```

| 分项 | 公式 | 含义 |
|:---|:---|:---|
| 位次激励 | `max(0, 120 - rank)` | 直接采信平台编辑排名意图 |
| 热度倍率（带上限） | `min(hot_value / 10000, 160)` | 160 分安全阀，防止爆款淹没敏感信号 |
| 基座源奖励 | 微博/知乎 → +20 分 | 高权重核心信源加分 |

### 1.2 演算案例

| 场景 | 排名 | 热度 | 得分 |
|:---|:---|:---|:---|
| 微博顶流热搜 | #1 | 5,000,000 | `119 + 160 + 20 = 299`（理论峰值） |
| 二线平台中型热点 | #30 | 50,000 | `90 + 5 + 0 = 95` |
| 小众敏感信号 | #99 | 1,000 | `21 + 0.1 + 0 ≈ 21` |

## 2. 🟢 事件影响指数 (heat_score)

算法位置：`app/services/events.py` → `_build_cluster_payload()`

### 2.1 公式

```text
heat_score = avg(top3_article_scores) + min((platform_count - 1) × 30, 150) + log₂(article_count) × 15
```

| 分项 | 取值范围 | 含义 |
|:---|:---|:---|
| Top-3 文章热度均值 | 0 ~ 299 | 事件内最强信号强度 |
| 跨平台奖励 | 0 ~ 150 | 多域覆盖传播力 |
| 数量对数奖励 | 0 ~ ~100 | 信息量边际递减增益 |

### 2.2 演算案例

| 事件 | Top-3 均分 | 平台数 | 文章数 | heat_score |
|:---|:---:|:---:|:---:|:---:|
| 顶级跨域 | 280 | 6 | 32 | `280 + 150 + 75 = 505` |
| 单平台热点 | 200 | 1 | 8 | `200 + 0 + 45 = 245` |
| 低强度信号 | 50 | 1 | 2 | `50 + 0 + 15 = 65` |

## 4. 🟢 事件排序策略

算法位置：`app/api/routes.py` + 前端 `yujing-ui/src/App.vue::compareEvents`

### 4.1 默认排序（后端）

事件列表（`/api/events`）默认按 **`heat_score DESC, latest_article_time DESC, id DESC`** 排序。

### 4.2 时间窗口自适应

统一搜索 `/api/search/unified` 中：
- **长时间窗口（>24h）**: `article_count DESC, latest_article_time DESC, id DESC` → 热度优先
- **短时间窗口（≤24h）**: `latest_article_time DESC, article_count DESC, id DESC` → 时效优先

### 4.3 稳定化 tiebreaker（2026-04-22 新增）

**Bug 观察**：初版排序仅以 `heat_score / article_count / latest_article_time` 为键，同值行在 SQLite 中返回顺序不确定；叠加 `limit(9)` 后每次刷新取到的 Top 9 集合都可能在同分事件间漂移，前端表现为"闪一下换卡片"。

**修法**：所有排序子句尾部统一加 `Event.id.desc()` 作稳定 tiebreaker，影响：

| 端点 | Before | After |
|:---|:---|:---|
| `/api/events` | `heat_score DESC, latest_article_time DESC` | + `id DESC` |
| `/api/search/unified` (high_heat) | `article_count DESC, latest_article_time DESC` | + `id DESC` |
| `/api/search/unified` (短窗口) | `latest_article_time DESC, article_count DESC` | + `id DESC` |
| `search_events` (服务层) | `latest_article_time DESC, article_count DESC` | + `id DESC` |

### 4.4 前端 `compareEvents` 分级整数比较

前端对后端返回的事件再过一遍 `compareEvents` 稳定排序，为什么不用加权公式：

```js
// 失败方案（已废弃）：
// heat_score 是后端 rebuild 时写入的浮点，两次 Ctrl+F5 之间若 scheduler 触发过 rebuild
// 分数会微变→ sort 结果随之漂移；加权公式的浮点减法本身也可能引入 ±ε 的不稳定比较。
// score = article_count * 4 + platform_count * 6 + heat_score

// 最终方案（生产）：分级整数比较，同一批数据的顺序绝对稳定
const compareEvents = (a, b) => {
  if (a.article_count !== b.article_count) return b.article_count - a.article_count;
  if (a.platform_count !== b.platform_count) return b.platform_count - a.platform_count;
  return b.id - a.id;
};
```

### 4.5 双 fetch 并发双写修复

前端有两个地方会写 `events.value`：
- `watch(activePlatform, immediate: true)` → `scheduleEventHubHydration` → 旧 `fetchEvents` (`/api/events`)
- `onMounted` → `fetchUnifiedSearch` (`/api/search/unified`)

两个接口 ORDER BY 不同 + 各自 limit(9)，并发返回的两批事件集合**不完全相同**（一批以热度优先、一批以时间优先）→ 前后两次渲染换卡片。修法：`scheduleEventHubHydration` 不再调 `fetchEvents`，统一走 `fetchUnifiedSearch`，单一写入通道 + `requestId` + `AbortController` 并发保护。

## 4bis. 🟢 前端 `impactScore` （0-100 归一化影响指数）

算法位置：`yujing-ui/src/utils/dataAdapter.js::calculateImpactScore`

这是前端在添加组件层对热搜条目做的归一化影响力分数，与后端 `heat_score`（事件级）**相互独立**：后端 `heat_score` 度量事件级影响力（可达 500+），前端 `impactScore` 度量单条热搜的相对影响力（0-100）。

### 公式

```text
baseScore = max(40, 100 - rank * 1.5)
bonus = 平台加成（最多 +10）
impactScore = round(baseScore + bonus)   # 截断到 [0, 100]
```

| 条件 | 得分 |
|:---|:---|
| 热搜第 1 名 (rank=1) | baseScore = 98.5 |
| 第 10 名 (rank=10) | baseScore = 85 |
| 第 40 名 (rank=40) | baseScore = 40（触底） |
| 微博平台加成 | `min(10, hot_score / 200000)` |
| 知乎平台加成 | `min(10, hot_score / 100)` |
| B 站平台加成 | `min(10, view / 500000)` |
| 其他平台 | 0 |

### 演算案例

| 场景 | rank | hot_value | impactScore |
|:---|:---:|:---:|:---:|
| 微博顶流热搜 | #1 | 5,000,000 | `98.5 + 10 ≈ 99` |
| 知乎中型热点 | #8 | 3,000 | `88 + 10 = 98` |
| B 站尾部视频 | #45 | 100,000 | `40 + 0.2 ≈ 40` |

### 与 `heat_score` 的关系

| 概念 | 位置 | 度量 | 范围 |
|:---|:---|:---|:---|
| `impactScore` | 前端 | **单条热搜条目相对影响力**（rank+平台热度） | 0-100 |
| `heat_score` | 后端 | **事件级综合影响力**（Top3 文章得分+跨平台+数量） | 0-500+ |

前端卡片显示的"99 影响指数"来自 `impactScore`，描述该条热搜在当前平台的相对热度；事件列表排序按 `heat_score`（和前者无直接关系）。

## 5. 🟢 事件语义聚类：FAISS + 双层 Otsu（生产主路径）

算法位置：`app/services/semantic_index.py` → `cluster_articles_semantic_faiss()`
启用方式：`.env` 中 `SEMANTIC_CLUSTER=1`（当前生产默认配置）

### 5.1 流程总览

```
文章标题+摘要 → BGE 向量编码(512维) → FAISS IVF-Flat 近邻召回(Top-K=20)
    → 双层 Otsu 自适应阈值 → 纯 cosine 判定 + Union-Find 聚类
    → 簇内复核 → Canonical 硬合并边救回 → 最终事件簇
```

### 5.2 各步骤详解

**① 向量编码**
- 模型：`BAAI/bge-small-zh-v1.5`（512 维，L2 归一化）
- 输入：`标题 + "\n" + 摘要前 200 字`
- 持久化：SQLite `article_embeddings` 表 + FAISS 内存索引

**② FAISS 近邻召回**
- 索引类型：`IndexIVFFlat`（`nlist=64, nprobe=8, METRIC_INNER_PRODUCT`）
- 召回规模：每篇文章取 Top-K=20 近邻

**③ 复合相似度（仅用于诊断/排序，不参与聚类合并）**
```text
score = 0.60 × cosine_similarity + 0.25 × time_decay + 0.15 × platform_diversity
```
- `time_decay = exp(-Δhours / 12)` — 12 小时半衰期
- `platform_diversity`: 跨平台 → 1.0，同平台 → 0.0
- 复合分写入 `relation_score` 字段，供事件卡片内文章排序和诊断使用

**③b Union-Find 聚类判据**
- 实际合并判据为**纯 cosine 相似度 ≥ 双层 Otsu L2 阈值**
- 双层 Otsu 从全量 top-K cosine 分布自动计算，无需手动设置

**④ 双层 Otsu 自适应阈值**
- L1（过滤线）：全量 Top-K cosine 上做 Otsu 二分割 → 噪声 vs 候选
- L2（合并线）：候选组内再做 Otsu → 主题相似 vs 同事件
- 兜底：数据不足时固定阈值 0.65

**⑤ Union-Find 聚类**
- 纯 cosine ≥ L2 阈值的文章对通过并查集合并为同一簇

**⑥ 簇内复核**
- 每个成员与簇代表的 cosine 必须 ≥ threshold，否则踢出
- 解决链式传染问题（A≈B, B≈C 但 A≠C）

**⑦ Canonical 硬合并边**
- 对文章标题执行正则去噪（去标点/数字后缀/语气词），得到 canonical title
- Canonical title 完全相同的文章对注入 score=1.0 的边，强制合并
- 防止 ANN 召回漏掉词汇高度相似但向量边缘命中的文章对

**⑧ 代表选取**
- 评分：`0.6 × 语义中心性 + 0.4 × 热度`，最高分者为簇代表

**⑨ Expelled 回收**
- 被复核踢出的文章按 canonical title 精确合并
- 无匹配者成为单篇事件

### 5.3 参数表

| 参数 | 值 | 选择理由 |
|:---|:---|:---|
| 嵌入维度 | 512 | BGE-small-zh 输出 |
| FAISS nlist | 64 | 平衡召回率与速度 |
| FAISS nprobe | 8 | 探测 12.5% 桶 |
| Top-K 近邻 | 20 | 覆盖同事件多表述 |
| 兜底阈值 | 0.65 | Otsu 数据不足时 |

> **注意**：复合相似度权重（cosine 0.60 / time 0.25 / platform 0.15）仅用于 `relation_score` 排序/诊断字段，**不参与 Union-Find 聚类合并**。聚类合并的唯一判据是纯 cosine ≥ 双层 Otsu L2 阈值。

## 6. 🟡 Jaccard 聚类（降级回退路径）

算法位置：`app/services/events.py` → `_cluster_articles()` + `_merge_near_duplicate_clusters()`
触发条件：`SEMANTIC_CLUSTER=0`（关闭语义路径）或语义路径异常时自动降级

> ⚠️ **注意**：当前生产环境 `.env` 配置 `SEMANTIC_CLUSTER=1`，Jaccard 路径**仅在语义路径异常时作为 fallback 启用**。评测数据显示该路径 F1=0.471，远低于语义路径的 0.827。

### 6.1 算法

1. **IDF 加权 Jaccard**：jieba 分词后计算 token 集合的 IDF 加权 Jaccard（`_idf_weighted_jaccard()`）
2. **Canonical title 加分**：归一化标题完全一致 → +0.42 分
3. **合并判定**：`score ≥ 0.22` → 合并
4. **二次合并**：`_merge_near_duplicate_clusters()` 对相似簇再次合并

### 6.2 完整相似度公式

```text
score = idf_weighted_jaccard(tokens_a, tokens_b)
      + title_bonus (0~0.42)
      + shared_token_bonus (0~0.15)
      + synonym_bonus (0~0.08)
      + entity_overlap_bonus (±0.1)
```

### 6.3 为何保留为 Fallback

- 不依赖 GPU / 模型加载，纯 CPU 即可运行
- 在 embedding 模型不可用（内存不足/加载失败）时保证事件功能不中断
- 评测对比数据为论文提供了 baseline 参照

## 9. 🟢 Tool-Calling Agent 推理引擎

算法位置：`app/services/agent/loop.py` + `llm_adapter.py`

轻量自研 Agent 引擎（~270 行），仅依赖 `langchain-core + langchain-openai`。

### 9.1 ReAct 循环

```
System Prompt + History + User Query
        ↓
    LLM (DeepSeek V3, 流式)
        ↓
   ┌─ tool_calls → ThreadPoolExecutor 并发执行 → observations → 继续循环
   └─ pure content → Final Answer → 结束
```

- 硬上限：`MAX_STEPS=8`
- 连续错误 > 2 次终止
- 多工具并发：ThreadPoolExecutor (max_workers=4)

### 9.2 工具注册表（10 个原子能力）

| 工具 | 功能 |
|:---|:---|
| `search_events` | 关键词+时间窗口检索事件 |
| `get_event_detail` | 事件详情+关联文章 |
| `compare_events` | 多事件并列指标对比 |
| `compare_platforms` | 两平台舆情概况对比，输出驱动前端 CompareDashboard |
| `analyze_event_sentiment` | 按时间桶聚合 BERT 情绪序列 |
| `search_articles` | 关键词文章搜索 |
| `semantic_search_articles` | FAISS 向量语义搜索 |
| `list_hot_platforms` | 多平台热榜快照 |
| `get_morning_brief` | 当日早报内容 |
| `rank_events_by_sentiment` | 按情绪占比排序 Top-K |

### 9.3 多轮对话

前端构建最近 12 条（6 轮）user/assistant 历史，追问建议基于工具类型自动生成。

### 9.4 SSE 流式事件

| 事件 | 含义 |
|:---|:---|
| `llm_thinking` / `llm_thinking_delta` | LLM 推理中/增量文本 |
| `llm_done` | LLM 推理完成 |
| `tool_call` / `tool_result` | 工具调用/结果 |
| `final` | 最终研判结论 |
| `error` / `done` | 错误/循环结束 |

### 9.5 引用可溯源

System prompt 要求输出必须绑定 `event#<id>` / `article#<id>` 引用，前端正则识别后可点击验证原文。

- 构建 FAISS IVF-Flat 内存索引

### 14.2 在线检索精排

1. 用户 query → BGE 编码 → FAISS Top-K=20 近邻
2. 复合精排分：`0.6×cosine + 0.25×time_decay + 0.15×platform_diversity`
3. P95 自适应阈值截断低分候选
4. 返回语义近邻列表供 Agent `semantic_search_articles` 工具使用
