# 舆镜 YuJing — 系统设计与开发说明

---

## 一、系统总体架构

舆镜（YuJing）是一款全平台舆情监控与 AI 研判系统。整体架构自下而上分为五层：

```
┌───────────────────────────────────────────────────────────┐
│                    表现层（前端 UI）                        │
│         Vue 3 + Vite · ECharts · SSE 流式渲染              │
├───────────────────────────────────────────────────────────┤
│                  接口层（API Gateway）                      │
│        FastAPI REST + SSE · MeiliSearch 全文检索            │
├───────────────────────────────────────────────────────────┤
│                    算法层（AI 引擎）                        │
│  Tool-Calling Agent · BERT 情感 · BGE 向量 · LLM 研判      │
├───────────────────────────────────────────────────────────┤
│                    服务层（业务逻辑）                       │
│   事件聚合 · 语义索引 · 主题归并 · 推送检测 · 早报生成      │
├───────────────────────────────────────────────────────────┤
│                    数据层（采集 + 存储）                    │
│       8 平台爬虫 · SQLite/WAL · APScheduler 调度            │
└───────────────────────────────────────────────────────────┘
```

## 二、数据层

### 2.1 数据采集引擎

采集层基于 `app/crawler/` 实现，通过 APScheduler 以 **120 秒**为周期触发全量爬取，支持 8 个主流平台：

| 平台 | source_id | 认证方式 |
|:---|:---|:---|
| 微博热搜 | `weibo_hot` | Cookie |
| 百度热搜 | `baidu_hot` | Cookie |
| 今日头条 | `toutiao_hot` | Cookie |
| 知乎热榜 | `zhihu_hot` | Cookie |
| 哔哩哔哩 | `bilibili_hot_video` | Cookie |
| 财联社电报 | `cls_telegraph` | 公开 API |
| 华尔街见闻 | `wallstreet_news` | 公开 API |
| 澎湃新闻 | `thepaper_hot` | 公开 API |

**正文抽取**：通过 Jina Reader 将目标页面转为 Markdown，针对头条、B站、知乎等平台有专用解析逻辑（`reader.py`）。所有爬虫共享 `httpx.AsyncClient` 连接池，DB 写操作通过线程池隔离。

### 2.2 数据库设计

存储层使用 SQLite + SQLAlchemy，开启 **WAL 模式**（`PRAGMA journal_mode=WAL`），确保读写并发不相互阻塞。

核心数据模型（`app/database.py`）：

```
Article（原始情报）
  ├─ id, source_id, item_id（唯一标识）
  ├─ rank（平台原始排名）, hot_value（平台热度值）
  ├─ title, url, pub_date, fetch_time
  ├─ content（Jina 抓取的 Markdown 正文）
  ├─ ai_summary, ai_sentiment（AI 增强字段）
  └─ extra_info（JSON 扩展：阅读量/点赞等）

Event（聚合事件）
  ├─ id, title, summary, keywords（JSON）
  ├─ article_count, platform_count, heat_score
  ├─ sentiment, latest_article_time
  └─ representative_article_id, primary_source_id

EventArticle（事件-情报关联）
  ├─ event_id, article_id
  ├─ relation_score（语义相关度）
  └─ importance_score, is_primary

Topic（宏观主题）
  ├─ id, title, summary, keywords
  ├─ event_count, article_count, platform_count
  └─ latest_event_time, representative_event_id

ArticleEmbedding（语义向量）
  ├─ article_id, model_name
  ├─ dim, vector（float32 bytes）
  └─ updated_at
```

**关系结构**：`Topic` → (多) `Event` → (多) `Article`，三级粒度分别对应宏观议题、具体事件、原始情报。

## 三、服务层

### 3.1 事件聚合引擎（`app/services/events.py`）

负责将碎片化的热榜条目聚合为有意义的事件单元。

**两阶段聚合策略**：
1. **标题规范化**：正则去除序号、括号、平台后缀，提取 Canonical Title
2. **Jaccard 相似度聚类**：对 jieba 分词后的词集计算 Jaccard 系数，合并阈值 0.22；同一 Canonical Title 强制合并（+0.42 叠加）

**热度评分公式**：

单篇文章评分：
$$\text{Score} = \max(0,\ 120 - \text{rank}) + \min\!\left(\frac{\text{hot\_value}}{10000},\ 160\right) + \text{source\_bonus}$$

事件影响指数（`heat_score`）：
$$\text{heat\_score} = \text{avg}(\text{Top3 Article Scores}) + \min\!\big((\text{platform\_count}-1)\times 30,\ 150\big) + \log_2(\text{article\_count})\times 15$$

三个分项分别体现信号强度、跨域传播力、信息量边际递减增益。

### 3.2 语义向量索引（`app/services/semantic_index.py`）

基于 Sentence-BERT 实现文章语义相似度计算，支撑语义聚类与 Agent 工具检索。

- **嵌入模型**：`BAAI/bge-small-zh-v1.5`（512 维），增量生成，向量持久化到 `ArticleEmbedding` 表
- **索引结构**：FAISS IVF-Flat，内存驻留，启动时从 DB 重建
- **聚类合并**：FAISS 召回 top-K=20 近邻，基于纯 cosine 相似度 + Union-Find 聚类
- **阈值自适应**：双层 Otsu 算法自动计算最优分割阈值，兜底下限 0.65
- **复合 relation_score**：`0.6×cosine + 0.25×时间衰减 + 0.15×平台多样性`，仅用于关联排序，不参与合并判断

### 3.3 情感分析引擎（`app/services/emotion.py`）

**单引擎架构**，兼顾响应速度与分析精度：

| 引擎 | 模型 | 标签 | 用途 |
|:---|:---|:---|:---|
| EmotionEngine | `Johnson8187/Chinese-Emotion` | 8 维（中性/关注/喜悦/愤怒/悲伤/质疑/惊讶/厌恶） | 情感分布条形图 + 舆情倾向饼图 |
| 规则引擎（fallback） | 关键词字典匹配 | 8 维（与 EmotionEngine 对齐） | 模型未就绪时的响应级兜底 |

**请求链路保护**：BERT 模型通过后台守护线程加载（`_start_background_load`），不阻塞 API 启动。请求到来时模型未就绪则降级到关键词规则引擎，保证首次打开事件即有情绪分布图，同时不会因 BERT 同步推理把 CPU 打满。

**事件情绪后台补全**：专用 `max_workers=1` executor，同一时刻只跑 1 个 BERT 批次；`in-flight set` 去重，同一 event_id 不重复入队；`analyze_batch` 批量推理后写库，精标结果下次请求直接读取。

### 3.4 主题归并（`app/services/topics.py`）

对事件层再做一次语义聚合，将同一议题下的多个事件归并为 `Topic`。同样基于 BGE 向量 + cosine 相似度，阈值略高（0.70），保证主题粒度更粗。

### 3.5 全文检索（`app/services/search_engine.py`）

封装 MeiliSearch（端口 7700，随后端进程自动启动），支持：
- 模糊中文全文检索
- 12 分制逻辑重排：标题全词 +12、关键词 +8、正文摘要 +5
- 统一搜索接口：一次查询同时返回 Event、Topic、Article 三类结果

## 四、算法层

### 4.1 Tool-Calling Agent（`app/services/agent/`）

轻量自研 Agent 引擎，约 270 行核心代码，仅依赖 `langchain-core + langchain-openai`，不引入 LangGraph/AutoGen。

**架构组成**：

| 文件 | 职责 |
|:---|:---|
| `loop.py` | 观察-思考-行动主循环，MAX_STEPS=8 |
| `registry.py` | ToolSpec 注册表，自动编译 OpenAI function schema |
| `llm_adapter.py` | DeepSeek/LangChain 调用抽象（流式 + 同步） |
| `schemas.py` | AgentStep / Trajectory / ToolCall 数据类 |
| `tools/` | 10 个原子工具 handler |

**10 个注册工具**：

| 工具名 | 功能 |
|:---|:---|
| `search_events` | 关键词 + 时间窗口检索事件 |
| `get_event_detail` | 事件详情 + Top-K 关联文章 |
| `compare_events` | 多事件并列指标对比（热度/情绪/平台） |
| `compare_platforms` | 两平台舆情概况对比（情报规模/情绪/24h 变化/7 日曲线/代表情报），直接驱动前端 CompareDashboard |
| `analyze_event_sentiment` | 按时间桶聚合情绪序列 |
| `search_articles` | 关键词文章搜索 |
| `semantic_search_articles` | FAISS 向量语义搜索 |
| `list_hot_platforms` | 多平台热榜快照 |
| `get_morning_brief` | 当日早报直取 |
| `rank_events_by_sentiment` | 按情绪占比排序 Top-K 事件 |

**Agent Loop 执行流**：
```
1. 构造 system prompt + 多轮历史 + user query
2. 调用 DeepSeek 流式获取 tool_calls 或 final content
   ├─ 有 tool_calls → 多工具并发执行（ThreadPoolExecutor）
   │                 → 结果 append 为 tool 消息 → 回到步骤 2
   └─ 无 tool_calls → 当前 content 为 final，循环结束
3. 超过 MAX_STEPS=8 或连续错误 ≥ 2 次，强制终止给出 fallback 结论
```

**评测结果**（20 个真实查询）：

| 指标 | 结果 |
|:---|:---|
| 完成率 | 100% (20/20) |
| 工具召回率 | 95% |
| 平均步数 | 3.5（P95=6） |
| 平均延迟 | 26 s（P95=42 s） |
| 引用真实性 | 人工抽查全部可溯源 |

### 4.2 LLM 研判（`app/llm.py`）

调用 DeepSeek API（OpenAI 兼容接口），支持：
- **文章深度分析**：SSE 流式输出，首 token 延迟 < 2 s
- **事件宏观研判**：`analyze_topic_macro_stream`，结合事件列表生成态势报告
- **每日早报**：`_build_morning_brief_prompt` 聚合 TOP15 事件 + 近 30 条热搜构造 prompt

### 4.3 关键词提取（`app/keyword_extraction.py`）

基于 jieba 的双路提取：
- **TF-IDF 路径**：`extract_tags`，topK=40，去除纯符号词和纯数字词
- **TextRank 路径**：`textrank`，topK=40，同样过滤
- 两路合并去重，按权重排序后取 Top-30 作为词云数据

## 五、接口层

### 5.1 REST API（`app/api/routes.py`）

基于 FastAPI，主要端点：

| 方法 | 路径 | 功能 |
|:---|:---|:---|
| GET | `/api/articles` | 热榜文章列表 |
| GET | `/api/events` | 事件列表（热度排序 + `id DESC` tiebreaker） |
| GET | `/api/events/{id}` | 事件详情 + 关联文章 |
| GET | `/api/articles/{id}` | **轻量文章详情**（Agent 引用 `article#N` 未命中内存时前端 fallback） |
| GET | `/api/topics` | 主题列表 |
| GET | `/api/search/unified` | 统一搜索（事件+文章+主题） |
| GET | `/api/articles/{id}/analyze` | 文章 AI 深度分析（SSE） |
| GET | `/api/topics/{id}/analyze` | 主题宏观研判（SSE） |
| GET | `/api/ai/morning_brief` | 每日早报（SSE） |
| POST | `/api/ai/export_pdf` | AI 报告导出 PDF |
| POST | `/api/admin/rebuild_embeddings` | 重建语义向量索引 |

### 5.2 Agent API（`app/api/agent_routes.py`）

| 方法 | 路径 | 功能 |
|:---|:---|:---|
| POST | `/api/agent/chat` | Tool-Calling Agent 对话（`stream=true` SSE 流式 / `stream=false` 同步阻塞） |

### 5.3 SSE 流式推送协议

文章分析与 Agent 对话均采用 `text/event-stream`，事件类型：

```
status        → 阶段状态提示
metadata      → 词云/情感/舆情分组数据
content_start → LLM 正文开始
content_delta → LLM 流式 token
content_end   → LLM 正文结束
llm_thinking  → Agent 推理过程（流式）
tool_call     → 工具调用记录
tool_result   → 工具执行结果
final         → Agent 最终结论
done          → 流结束
```

## 七、关键设计决策

### 7.1 为什么不用 LangGraph/AutoGen

- 自研 Agent Loop (~270 行) 具备完整的 11 个单测，全部离线（FakeLLM 注入）
- 切换 LLM Provider 只改 `llm_adapter.py` 一个文件
- 无黑盒中间层，推理链路完全可审计

### 7.2 为什么选 SQLite 而非 PostgreSQL

- 部署零依赖（单文件数据库）
- WAL 模式 + `busy_timeout=30s` 满足多读一写并发需求
- 当前数据规模（数万条）不构成 SQLite 性能瓶颈

### 7.3 BERT 推理不在请求链路上同步执行

- BERT 单次前向传播约 100-500ms，同步调用会将 API 延迟提升 5-10x
- 采用"规则兜底响应 + 后台单线程队列精标"双轨模式
- `max_workers=1` 的专属 executor 保证任意时刻最多 1 个 BERT 批次在运行，避免 CPU 饥饿

### 7.4 向量索引内存驻留而非每次查询重建

- FAISS IVF-Flat 索引构建耗时约 10-30s（10万条文章规模）
- 启动时一次性构建，缓存在内存，查询延迟 < 5ms
- 增量更新通过定期调用 `/api/admin/rebuild_embeddings` 触发
