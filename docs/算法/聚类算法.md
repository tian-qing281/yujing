# 聚类算法

> 最后更新 2026-05-18 · 对齐代码版本 · 主入口 [app/services/semantic_cluster.py](../../app/services/semantic_cluster.py) / [app/services/incremental_cluster.py](../../app/services/incremental_cluster.py)

## 1. 设计目标

把分散在 8 个平台的同一条「新闻事件」聚到一个 `Event` 实体下，解决：

1. 跨平台同题不同表述（“雷军 SU7”/“小米 SU7 Ultra”/“小米汽车”）。
2. 时序漂移：早期突发 → 长尾持续，要能持续合并新文章而不把老簇撕裂。
3. 性能：万级文章必须秒级出结果，且支持每 5 min 增量。

## 2. 整体架构

```
┌──────────────┐         ┌──────────────┐         ┌──────────────┐
│ 全量重建      │ ──→     │ 语义聚类      │ ──→     │  Event 表    │
│ (admin 触发)  │         │ (semantic_*) │         │ + Centroid   │
└──────────────┘         └──────────────┘         └──────────────┘
                                                          ↑
┌──────────────┐         ┌──────────────┐                 │
│ 每 30min     │ ──→     │ 增量聚类     │ ────────────────┘
│ APScheduler  │         │ (incremental)│  挂到最近 7 天事件
└──────────────┘         └──────────────┘
```

两条路径共用：BGE 向量、L2 归一、Centroid 平均更新公式。

## 3. 语义聚类（全量）

文件 [app/services/semantic_cluster.py](../../app/services/semantic_cluster.py)。

### 3.1 输入

- 最近 `LOOKBACK_HOURS`（默认 168h = 7 天）内的所有 `Article`
- 通过 [embedding_service](../../app/services/embedding_service.py) 计算 / 取缓存（512 维 BGE）

### 3.2 流程

1. **预处理**：拼接 `title + summary[:200]`，过滤纯空 / 长度 < 4 的文本。
2. **向量化**：批量 `encode(batch_size=16, max_length=128)`，L2 归一后写入 `ArticleEmbedding` 表（永久缓存）。
3. **FAISS 召回**：构造 `IndexFlatIP`（数量 < 5000）或 `IndexIVFFlat`（NLIST=64），每点取 `SEMANTIC_TOPK=20` 个近邻。
4. **复合相似度**：

   $$
   \text{score} = 0.60 \cdot \cos(v_i, v_j) + 0.25 \cdot \text{time}(t_i, t_j) + 0.15 \cdot \text{platform}(p_i, p_j)
   $$

   - `time` 项：$\exp(-\ln 2 \cdot |\Delta t| / 12h)$（半衰期 12h）
   - `platform` 项：同源=1.0，跨源=0.5
5. **Union-Find 合并**：score ≥ `SEMANTIC_CLUSTER_THRESHOLD = 0.62` 即连边。
6. **生成 Event**：
   - 选 `heat_score` 最高文章的 `title` 作为事件标题
   - centroid = 簇内所有向量的算术平均（再 L2 归一）
   - 写 `Event` + `EventArticle` 关联表

### 3.3 关键常量

| 参数 | 默认 | 出处 |
|------|------|------|
| `SEMANTIC_CLUSTER_THRESHOLD` | 0.62 | `os.getenv` |
| `SEMANTIC_TOPK` | 20 | 同上 |
| `SEMANTIC_TIME_HALF_LIFE_HOURS` | 12 | 同上 |
| `EMBED_DIM` | 512 | bge-small-zh-v1.5 |
| `NLIST` / `NPROBE` | 64 / 8 | FAISS IVF |

## 4. 增量聚类

文件 [app/services/incremental_cluster.py](../../app/services/incremental_cluster.py)。

每 30 min 调度（[app/scheduler.py](../../app/scheduler.py)）：

1. 取近 5 min 新入库、未关联事件的文章
2. 取近 `INCR_CLUSTER_LOOKBACK_HOURS = 168h` 的 Event centroid，构 FAISS 索引
3. 对每篇新文章：召回 TopK，按相同复合公式打分
4. **判定**：最大 score ≥ `INCR_CLUSTER_THRESHOLD = 0.69` → 挂到该事件；否则建立新事件
5. **Centroid 更新**：$c' = \text{L2}\bigl(c \cdot \frac{n}{n+1} + v \cdot \frac{1}{n+1}\bigr)$
6. 同步更新 `Event.heat_score`、`updated_at`、`article_count`

> 阈值比全量高（0.69 vs 0.62）：增量决策不可逆，宁可保守新建簇也不要污染老簇。

## 5. Centroid 校准

每 2h（[scheduler.py](../../app/scheduler.py)）`_run_centroid_calibrate_job`：

- 对每个近 7 天活跃 Event 重新拉所有 `EventArticle.article_id`
- 重新算 centroid = 平均所有向量 → 写回 `Event.centroid`
- 修正增量聚类长期漂移

## 6. 双轨：Jaccard 兜底

如果未启用 BGE（`SEMANTIC_CLUSTER=0` 或环境缺依赖），自动降级到 [legacy_cluster.py](../../app/services/legacy_cluster.py)：

- 关键词集合（jieba TextRank Top12）做 Jaccard 相似
- 阈值 0.35
- 性能更高、效果次之；保留作为最小可运行版本

## 7. 性能数据

| 场景 | 规模 | 耗时（i7-12700H, CPU） |
|------|------|------|
| 全量语义聚类 | 5000 篇 → ~600 事件 | ≈ 500 ms（不含向量化）|
| BGE 向量化首次 | 5000 篇 | ≈ 35 s（batch=16）|
| 向量化缓存命中 | 90%+ | 跳过 |
| 增量聚类 | 100 新篇 + 1000 事件 | ≈ 50 ms |
| Centroid 校准 | 1000 事件 | ≈ 200 ms |

## 8. 调用入口

| 入口 | 触发 | 函数 |
|------|------|------|
| `POST /admin/events/rebuild` | 人工 | `semantic_cluster.rebuild_events(...)` |
| `POST /admin/events/incremental` | 人工 | `incremental_cluster.run_incremental(...)` |
| APScheduler | 每 30 min | `_run_incremental_cluster_job` |
| APScheduler | 每 2 h | `_run_centroid_calibrate_job` |

<summary><b>面试问答</b></summary>

**Q1：阈值 0.62 / 0.69 怎么定的？**
A：用线下小样本（≈ 200 标注对）做 P-R 曲线，0.62 在召回 ≈ 0.82 时精度 ≈ 0.91；增量决策不可逆所以再上浮 0.07 保守。

**Q2：为什么不用 HDBSCAN / OPTICS？**
A：（1）这俩需要全量数据，不适合每 5 min 来 100 篇的增量；（2）我们已有「Event = 簇」的持久化实体，HDBSCAN 重跑会打乱簇 id。Union-Find + 阈值的好处是：可拆解成「全量重建」和「增量挂载」两条路径，且 centroid 平均更新简单稳定。

**Q3：复合相似度里 time 权重 0.25 是不是太低？**
A：BGE 向量已经对内容相似度敏感，时间只是辅助消歧。如果调到 0.5，两条间隔 24h 的相同事件会被切断（exp 衰减下 24h 半衰 → time 项只剩 0.25）；0.25 实测能合并 3-5 天的长尾。

**Q4：FAISS 用 IndexFlatIP 还是 IVF？**
A：< 5000 篇直接 FlatIP（精确）；超过则 IVF + NLIST=64 NPROBE=8。L2 归一后内积 = 余弦相似度，省一次开方。

**Q5：Centroid 平均更新会不会越来越偏？**
A：会，所以每 2h 跑一次校准重新算平均。增量更新的偏差累积主要来自顺序敏感（早期文章权重高于晚期），校准就是消除这种顺序偏。

**Q6：怎么处理两个相似事件应该合并的情况？**
A：目前没有「事件 → 事件」合并通路。线下做法是 admin 触发全量 rebuild_events，新一轮会把它们合到一起。在线合并风险大（影响订阅/画像），暂未实现。

**Q7：跨语种 / 跨平台口径不一致怎么办？**
A：BGE-small-zh 对中文短句鲁棒；平台口径不一致正是引入 platform 项的原因（同源 +0.15 bonus 抵抗噪声）。英文混杂场景下计划替换为 bge-m3 多语模型。

</details>
